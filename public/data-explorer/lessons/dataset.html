Getting to know your data

What this lesson is for

In the first lesson you learned to press Run and read the answer. Before you start asking questions of your data — which site landed the most fish? how much tilapia last month? — it helps to know how your data is arranged: what one line in the table stands for, how the lines fit together, and what each column is telling you.

That is all this lesson does. Once the shape of the data is clear, the next lessons will make sense. Go slowly, press Run on each box, and remember: you cannot break anything.

Where your data comes from

Your data does not appear from nowhere. Every time an enumerator meets a fisher coming back to a landing site, they fill in a short survey: the date, the landing site, the boat and gear used, how many people fished, and what was caught.

All of those surveys, from every landing site, are collected into one big table. That table is your data. Reading it is simply reading those survey records, stacked one on top of another.

A table has two simple parts:

  • a row is one line going across — one record;
  • a column is one heading going down — one piece of information that was recorded, like the date or the weight.

The rest of this lesson is about what the rows and columns in your table mean.

A small example to look at

It is easier to see the shape on a small table first. Here is a made-up example — just two fishing trips, with each trip shown in its own colour.

survey_1 trip_1 2024-01-05 Shimoni hand line Tilapia 12 3 20
survey_1 trip_1 2024-01-05 Shimoni hand line Snapper 5 3 20
survey_1 trip_1 2024-01-05 Shimoni hand line Octopus 3 3 20
survey_2 trip_2 2024-01-06 Vanga gillnet Tilapia 8 2 14
survey_2 trip_2 2024-01-06 Vanga gillnet Snapper 6 2 14

Trip 1    Trip 2

Take a moment to read it. Notice that some things repeat down the table while others change on every line — we will come back to that, because it is the key to understanding your data.

What one row means

Look at the very first line. It is one catch: Tilapia, 12 kg. The second line is another catch: Snapper, 5 kg.

Each row is one catch — one kind of fish from one trip.

This is the first thing to hold on to. A row is not a whole trip, and it is not one fisher. It is one kind of fish that was recorded. So if a single trip brought back three kinds of fish, that trip fills three rows.

How the rows fit into trips

You may have noticed something that confuses almost everyone at first: the same site, the same date and the same trip_id appear on several lines. Nothing is wrong — this is exactly how the data is meant to look.

The reason is simple: one fishing trip usually brings back more than one kind of fish. Each trip is given an identity code, trip_id (and survey_id, the survey it came from). Every kind of fish from that trip gets its own row, and they all carry the same trip_id. That shared code is how you know which rows belong to the same trip.

In the example, trip_1 brought back three kinds of fish, so it fills three rows. trip_2 brought back two, so it fills two rows. Here is that first trip drawn as a picture:

Two kinds of columns

Now look across the columns. Once you see it, you cannot un-see it: the columns fall into two groups. (Here the colours mark the two kinds of columns — not the trips as before.)

About the trip (same on every row)
landing_date, site, gear, n_fishers, tot_catch_kg …
About each catch (changes on each row)
fish (catch_taxon), catch_kg, length_cm, catch_price

Some columns describe the whole trip. They are the same on every row of that trip, because the trip happened once: landing_date, site, gear, and tot_catch_kg — the total weight the trip brought in.

Other columns describe each catch on its own, so they change from row to row: fish, and catch_kg — the weight of that one kind of fish.

This difference matters in real work. tot_catch_kg is the whole trip’s weight; catch_kg is one fish’s weight. If you added up tot_catch_kg over every row, you would count the same trip several times and get a number far too big. For a trip total you use tot_catch_kg; for a single catch you use catch_kg.

You do not need to memorise the columns — the next lessons introduce them one at a time. For now, just hold the shape in your head: rows are catches, rows group into trips, and every column is either about the trip or about the catch.

Looking at your own data

You now know the shape. Let’s load your real landing records — the same data you can open in the Data Download tab — into the same kind of table. Press Run; the first time it may take a few seconds.

// Fetch the signed-in user's capped, permission-filtered landings as JSON, reusing the API base URL
// the React app publishes to localStorage (getApiBaseUrl). Same bridge as Lesson 1.
landings_data = {
  const token = localStorage.getItem("authToken");
  if (!token) return [];
  const apiBase = localStorage.getItem("apiBaseUrl") || "/api";
  const res = await fetch(`${apiBase}/data-download/explorer-data`, {
    headers: { Authorization: `Bearer ${token}`, Accept: "application/json" }
  });
  if (!res.ok) { console.warn(`explorer-data fetch failed: ${res.status}`); return []; }
  return await res.json();
}

This is your real data, and it has the same shape as the small example. Try typing the name of your landing site, or a fish, into the search box — or click a column heading to sort. Looking around like this is the best way to get a feel for what you actually have.

How big is your data

Two simple questions help you get your bearings: how many records do you have, and how many columns describe each one? Press Run:

The first number is how many catch records you hold — often many thousands. The second is how many pieces of information are kept about each catch. This is far more than you could read by eye in a spreadsheet, which is exactly why we use R: it can look through all of it for you in a moment, which is what the next lessons will do.

What each column means

Finally, let’s see the columns by name. Press Run to list them:

These are the headings in your table. Below is what the main ones mean, grouped the same way we saw above. Keep this nearby — it is the dictionary for your data.

Which trip a row belongs to

Column Meaning
survey_id The survey this record came from
trip_id The fishing trip. Rows with the same trip_id are from the same trip
n_catch How many kinds of catch that trip recorded

About the trip (same on every row of the trip)

Column Meaning
landing_date The day the catch was brought to shore
gaul_2_name The district / area
gear The fishing method (e.g. hand line, gillnet)
vessel_type The boat used (e.g. dhow)
n_fishers How many people were fishing
trip_duration_hrs How many hours the trip lasted
catch_habitat Where they fished (e.g. reef)
tot_catch_kg Total weight of the whole trip, in kg
tot_catch_price Total value of the whole trip

About each catch (one row each)

Column Meaning
catch_taxon The fish type, as a short FAO code (e.g. SKJ = skipjack tuna)
scientific_name The fish’s scientific (Latin) name
length_cm The fish length, in centimetres
catch_kg The weight of that catch, in kg
catch_price The value of that catch

In your real data the fish appears as a short code in catch_taxon (for example SKJ). The scientific_name column gives its full name. We used everyday names in the small example above just to keep it easy to read.

What you have learned

You can now read the shape of your data:

  • a row is one catch — one kind of fish from one trip;
  • rows belong together when they share a trip_id, and n_catch says how many a trip had;
  • every column is either about the trip (the same on every row) or about each catch (different on each row);
  • your real data has this same shape — just much bigger.

That is the foundation. In the next lesson you will start to find the rows you need — for example, showing only the landings from your site, or only one month.
